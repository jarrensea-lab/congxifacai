# 恭喜发财 v8 盈利系统顶层逻辑与架构审查

日期：2026-07-03  
范围：`/Users/zhuchenyuan/AI/workflows/恭喜发财`  
定位：顶层逻辑、项目目标、系统架构、矛盾诊断和整改方向  
边界：本项目是 A 股研究、策略、风控、报告和预警助手，不自动真实下单；所有输出用于人工复核。

## 0. 结论先行

恭喜发财不应该被理解成“AI 每天猜一只股票”的工具，也不应该被理解成“多生成几份研究报告”的系统。

它应该被设计成一个小账户盈利操作系统：

```text
发现主线
  -> 找到可交易标的
  -> 判断市场状态
  -> 选择交易剧本
  -> 计算风险预算和仓位
  -> 触发人工复核
  -> 记录结果
  -> 复盘校准下一次决策
```

当前 v7.5 已经搭好了很多正确地基：账户可执行性、Target Pool 分层、Target Snapshot、Evidence Ledger、主报告操作优先、Sentinel / Serenity 研究边界。

但当前最核心的问题是：交易决策层仍然像一个单体评分器，而不是一个盈利系统。

所以整改方向不是“把风控放松一点”，也不是“删掉 Sentinel/Serenity”，而是进入 v8：

```text
Regime 市场状态
  + Playbook 交易剧本
  + Risk Budget 风险预算
  + Event Alert 事件预警
  + Performance Ledger 复盘闭环
```

## 1. 项目目标

### 1.1 唯一主目标

本项目的唯一主目标是：

> 提高真实账户在可承受风险内获得正收益的概率。

更具体地说：

1. 选出标的。
2. 给出可执行策略。
3. 用户按策略人工复核并操作。
4. 通过复盘和数据闭环持续提高盈利能力。

所有模块都必须服务这个目标。不能提高候选发现、策略准确率、风险控制、入场时机、退出时机或复盘质量的模块，都不应该占据生产主线。

### 1.2 项目不是这些东西

不是资讯聚合器。  
不是研究报告生成器。  
不是 AI 辩论表演系统。  
不是自动下单机器人。  
不是每天强行给买入建议的荐股器。  
不是以“观望”兜底来避免犯错的保守报告机。

### 1.3 项目的真实用户场景

用户每天需要的不是更多观点，而是更清楚的操作判断：

```text
现在账户是什么状态？
今天是否应该动？
如果买，买谁，多少钱，什么价格，错了哪里止损？
如果卖，卖谁，卖多少，看什么信号？
如果不动，下一次触发条件是什么？
这次判断以后如何复盘？
```

这决定了主报告和飞书提醒必须优先回答动作，而不是优先展示研究。

## 2. 整体盈利逻辑

### 2.1 正确的盈利闭环

```text
数据采集
  -> 证据归一
  -> 主线识别
  -> 标的生成
  -> 账户可执行过滤
  -> 市场状态判断
  -> 交易剧本选择
  -> 仓位和止损计算
  -> 事件触发提醒
  -> 人工复核
  -> 结果复盘
  -> 阈值和权重校准
```

### 2.2 AI agent 的优势位置

AI agent 不应该和量化机构拼毫秒级买点。它在这个项目里的优势应该是：

| 位置 | AI agent 应该做什么 | 不应该做什么 |
|---|---|---|
| 主线发现 | 从新闻、公告、主题、产业链里发现早期变化 | 直接说买入 |
| 证据整理 | 把碎片信息转成 evidence_id 和可复盘证据 | 编造来源或证据编号 |
| 替代标的 | 龙头买不起时找同产业链可交易替代 | 让买不起的龙头进入可执行池 |
| 风险扫描 | 找减持、亏损、监管、退市、题材退潮 | 用自然语言替代风控 gate |
| 盘中监控 | 盯触发条件，及时推送事件提醒 | 等午报再解释已经发生的机会 |
| 复盘校准 | 统计哪个证据、角色、剧本真的有效 | 每天重新生成一套无法追责的建议 |

### 2.3 人和 AI 的分工

```text
AI:
  发现、归纳、筛选、监控、提醒、复盘、解释

确定性规则:
  账户可执行性、风险预算、仓位上限、止损、状态迁移、数据完整性

用户:
  最终复核、交易执行、风险偏好确认、资金边界确认
```

AI 给建议，但不能越过账户、风控和人工确认。

### 3.2 核心对象

#### Account

账户是最高约束，不是报告附属信息。

关键字段：

- 可用现金。
- 总资产。
- 当前持仓。
- 已实现盈亏。
- 最大可承受单笔亏损。
- 最大可承受日亏损。
- 最大可承受周亏损。

#### Evidence

证据是策略系统的原材料。

每条证据必须能回答：

- 来源是什么？
- 什么时候产生？
- 指向哪个主题或标的？
- 是机会证据还是风险证据？
- 是否进入过 Target Pool？
- 后续表现如何？

#### Target

Target 不是简单股票代码，而是生命周期对象。

状态：

```text
research_reference -> watching -> executable -> position -> removed
                    \-> blocked_chasing
                    \-> dip_watch
                    \-> cooldown
```

#### Regime

Regime 是市场状态。

至少需要四类：

| 状态 | 含义 | 允许动作 |
|---|---|---|
| attack | 大盘和主线共振，赚钱效应强 | 潜伏、回踩、突破都可评估 |
| neutral | 震荡，结构机会存在 | 小仓潜伏、低吸，谨慎突破 |
| defense | 指数弱，板块轮动快 | 只允许低风险观察和持仓风控 |
| freeze | 冰点或单边下跌 | 禁止新开仓，只做风险处理 |

没有 Regime，低吸会变成接飞刀。

#### Playbook

Playbook 是交易剧本，不同机会必须走不同逻辑。

| Playbook | 适用场景 | 核心信号 |
|---|---|---|
| `theme_seed` | 主线早期潜伏 | 主题升温、标的低位、资金未明显派发 |
| `pullback_entry` | 强逻辑首次分歧低吸 | 回踩不破、分时不再创新低、资金流出收敛、板块仍强 |
| `breakout_entry` | 放量突破追随 | 量比、成交额、趋势确认、非追高区 |
| `risk_exit` | 持仓风险处理 | 止损、资金转弱、冲高回落、题材退潮 |
| `no_trade` | 风险过高或证据不足 | 冻结、追高、数据缺失、买不起 |

#### Risk Budget

风险预算必须先于仓位。

```text
单笔允许亏损金额 = 账户权益 * 单笔风险预算
仓位金额 = 单笔允许亏损金额 / 止损距离
最终仓位 = min(仓位金额, 单票上限, 可用现金 - 现金底线, 一手可买约束)
```

这比固定“单票 50%”更稳。

## 5. 当前核心问题

### 5.1 问题一：项目目标和交易决策层不匹配

目标是盈利闭环，但当前交易决策层更像一个报告评分器。

当前逻辑大致是：

```text
snapshot -> score_target -> buy/watch/research_only
```

这个模型太薄。它无法区分：

- 主线潜伏。
- 回踩低吸。
- 放量突破。
- 持仓卖出。
- 冰点禁买。
- 追高冷却。
- 研究参照转替代标的。

所以它会天然偏向“看到强势再买”，而不是“提前发现、等待触发、按剧本执行”。

### 5.2 问题二：风控参数和收益目标互相拧巴

当前 `growth_sprint` 目标是 30 天争取 +10%，但参数是：

- 单票上限 50%。
- 单笔硬止损 5%。
- 账户最大回撤 -10%。

如果半仓触发 5% 止损，账户损失约 2.5%。连续 4 次失败就接近 -10% 回撤红线。

这不是“太保守”或“太激进”单独能描述的问题，而是风控单位错了：

```text
现在按仓位上限控制风险
应该按每笔允许亏损金额控制风险
```

### 5.3 问题三：强势确认逻辑被误当成总策略

强势确认适合少数场景，但不能成为唯一盈利逻辑。

当前买入倾向依赖：

- 涨幅达到强势阈值。
- 量比放大。
- 成交额足够。
- 非接近涨停。

这能防止乱买，但会带来两个问题：

1. 容易买在日内情绪高点。
2. 错过 AI agent 最有优势的提前发现和候选孵化。

强势确认应该降级为 `breakout_entry`，只是 Playbook 之一。

### 5.4 问题四：低吸逻辑只有文字，没有系统

当前文档和报告里已有“等回踩确认”的表达，但系统没有真正的 `pullback_entry`。

缺少：

- 市场状态过滤。
- 板块相对强弱。
- 前低/支撑/均线计算。
- 分时不再创新低。
- 二次回踩不破。
- 资金流出收敛。
- 回踩失败后的冷却和出池。

没有这些，低吸会变成接飞刀。

### 5.5 问题五：Sentinel / Serenity 的价值没有完全进入交易闭环

Sentinel 和 Serenity 不应该被删。问题是它们现在还没有完全变成盈利系统的一部分。

正确用法：

```text
Sentinel:
  主题热度、新闻密度、风险事件、证据编号、候选发现

Serenity:
  产业链卡点、真实受益环节、龙头替代标的、过热风险

交易系统:
  只在账户、Regime、Playbook、风控都通过后才允许交易
```

### 5.6 问题六：事件触发不足，报告节奏太慢

日报和午报适合总结，不适合抓短线触发。

真正关键的窗口通常是：

- 09:30 到 10:00。
- 10:30 左右的第一次分歧修复。
- 14:30 到 14:50。
- 尾盘风险或抢筹。

因此飞书应该从“报告推送”扩展为“事件预警”。

### 5.7 问题七：复盘没有形成调参权力

如果复盘只记录结果，不影响下一次阈值、权重、候选池和 playbook，那它只是归档。

真正的复盘应该输出：

- 哪条 evidence 有效。
- 哪个主题有效。
- 哪个 playbook 有效。
- 哪个角色误判。
- 哪个阈值导致错过或亏损。
- 下次如何调整。

## 6. 必须推倒重来的部分

### 6.1 推倒 `score_target()` 作为交易决策中心

`score_target()` 可以保留为评分卡生成器，但不能继续作为总决策中心。

新结构：

```text
TargetSnapshot
  -> ScoreCard
  -> RegimeFilter
  -> PlaybookRouter
  -> PositionSizing
  -> ActionDecision
```

### 6.2 推倒固定止损和固定目标

固定 5% 止损、12% 目标太粗。

新止损来源应该按 playbook 区分：

| Playbook | 止损依据 |
|---|---|
| theme_seed | 题材失效 + 关键均线/前低 |
| pullback_entry | 回踩低点/前低/ATR |
| breakout_entry | 突破失败价/放量阴线/ATR |
| risk_exit | 持仓成本、硬止损、资金转弱 |

### 6.3 推倒固定单票上限作为仓位逻辑

单票上限只能是最后一道 ceiling。

核心仓位逻辑必须改为：

```text
我最多愿意亏多少钱？
止损距离是多少？
因此可以买多少钱？
```

### 6.4 推倒静态小账户种子作为主机会源

静态种子可以作为 fallback，但不能作为主 alpha。

主机会源应该是：

```text
Sentinel 主题
  -> 龙头 / 受益链条
  -> Serenity 找可交易替代
  -> 账户过滤
  -> Target Pool watching
```

## 7. 应该删除或降级的部分

| 内容 | 处理 | 原因 |
|---|---|---|
| 主报告长篇辩论原文 | 删除出主报告，转归档 | 占注意力，不直接产生动作 |
| 固定“唯一实盘狙击”表达 | 降级 | 只有真的 executable 才能这样写 |
| LLM 裁判直接给买卖结论 | 降级为解释层 | 最终动作必须由确定性规则生成 |
| 静态小账户种子 | 降级为 fallback | 不能长期作为机会来源 |
| 泛化“等放量突破” | 降级为 breakout playbook | 不能覆盖所有交易场景 |

## 9. 应该新建的模块

### 9.1 `market_regime.py`

职责：判断当前是否允许进攻。

输入：

- 指数涨跌。
- 市场成交额。
- 涨跌家数。
- 连板/跌停/涨停情绪。
- 板块强度。
- 北向或主力资金。

输出：

```json
{
  "regime": "attack|neutral|defense|freeze",
  "allowed_playbooks": ["theme_seed", "pullback_entry"],
  "risk_multiplier": 0.5,
  "reason": "指数弱，题材轮动快，禁止突破追涨"
}
```

### 9.2 `playbook_engine.py`

职责：根据标的状态和市场状态选择交易剧本。

输出：

```json
{
  "playbook": "pullback_entry",
  "action": "watch|buy|sell|remove",
  "entry_trigger": "...",
  "invalid_trigger": "...",
  "stop_loss": 0,
  "target_price": 0,
  "confidence": 0,
  "evidence_ids": []
}
```

### 9.3 `position_sizing.py`

职责：按风险预算倒推仓位。

输出：

```json
{
  "risk_amount": 60.85,
  "stop_distance_pct": 4.8,
  "raw_position_amount": 1267.7,
  "lot_adjusted_amount": 1280.0,
  "final_position_amount": 1280.0,
  "block_reason": ""
}
```

### 9.4 `theme_to_targets.py`

职责：把主题转成可交易标的。

流程：

```text
Sentinel 主题
  -> 龙头识别
  -> Serenity 产业链拆解
  -> 同链条低价/中低价替代
  -> 流动性过滤
  -> 账户过滤
  -> watching
```

### 9.5 `radar_pool.py`

职责：持久化池外雷达候选，避免把 radar 当 executable。

状态：

```text
radar_candidate -> watching -> executable
radar_candidate -> expired
radar_candidate -> removed
```

### 9.6 `event_alert_engine.py`

职责：盘中事件触发。

触发器：

- 回踩不破。
- 分时不再创新低。
- 资金流出收敛。
- 板块强度转强。
- 放量突破但未追高。
- 跌破止损。
- 冲高回落。
- 风险公告。

### 9.7 `performance_ledger.py`

职责：复盘归因。

维度：

- evidence_id。
- target_code。
- playbook。
- action。
- entry_price。
- stop_loss。
- target_price。
- 1/3/5/20 日收益。
- 最大浮亏。
- 是否触发止损。
- 是否错失机会。
- 结论：升权、降权、冷却、删除。

## 10. 整改路线

### Phase 1：先把交易决策层推倒重建

目标：不再让 `score_target()` 单独决定交易。

任务：

1. 新建 `market_regime.py`。
2. 新建 `position_sizing.py`。
3. 新建 `playbook_engine.py`。
4. `target_scoring.py` 改为只输出 ScoreCard。
5. 报告读取 Playbook 输出，而不是直接读取 buy/watch。

验收：

- 同一个标的在不同 regime 下会得到不同动作。
- 仓位由风险预算倒推，不由固定 50% 决定。
- `breakout_entry`、`pullback_entry`、`theme_seed` 有清晰区分。

### Phase 2：建立动态候选发现

目标：小账户机会不再依赖静态种子。

任务：

1. 新建 `theme_to_targets.py`。
2. Sentinel 主题进入候选生成。
3. Serenity 输出小账户可交易替代。
4. 静态种子只作为 fallback。
5. Target Pool 增加 `dip_watch`、`cooldown`、`risk_alert`。

验收：

- 当高价龙头买不起时，系统能输出同产业链可交易替代。
- 候选有 evidence_id、主题、入池理由、阻塞理由。

### Phase 3：盘中事件型提醒

目标：飞书不再只等报告。

任务：

1. 新建 `event_alert_engine.py`。
2. 增加观察池触发器。
3. 增加持仓风险触发器。
4. 09:30-10:00 和 14:30-14:50 增加重点扫描。

验收：

- 观察池触发后能推送明确动作。
- 风险触发后能推送止损或减仓复核。
- 日报只总结，不承担所有机会发现。

### Phase 4：复盘闭环

目标：系统开始学习，而不是每天重新猜。

任务：

1. 新建 `performance_ledger.py`。
2. 记录每条 action 的后续收益。
3. 按 playbook 统计胜率、盈亏比、最大回撤。
4. 按 evidence_id 统计有效性。
5. 生成阈值调整建议。

验收：

- 每个 playbook 有 1/3/5/20 日表现。
- 系统能说明哪个策略在近期有效，哪个需要降权。

## 12. 外部调研对本项目的启发

近期 LLM trading / agentic finance 研究给出的共同信号是：

1. LLM 直接择时在长周期并不稳定，容易在牛市过保守、熊市过激进。
2. 交易 agent 的瓶颈不是模型能不能写理由，而是执行语义、交易成本、时间切分、证据账本和可复现评估。
3. 资产管理中的 agent 更适合做人类监督下的监控、证据整理、研究加速和异常提醒。

因此，本项目的正确方向不是让 LLM 直接决定买卖，而是让 AI agent 成为：

```text
主线发现器
证据归一器
替代标的生成器
事件监控器
复盘分析器
```

确定性策略层负责：

```text
能不能买
买多少
哪里止损
什么条件取消
什么条件卖出
```

恭喜发财 v8 应该推倒交易决策层，不推倒项目本身。

保留 v7.5 的数据、证据、账户和报告地基；把单一强势确认评分器升级为市场状态、交易剧本、风险预算、事件提醒和复盘校准组成的盈利操作系统。
