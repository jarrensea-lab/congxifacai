# 盈利真值优化设计

日期：2026-07-24
状态：待用户确认
目标：让每一条生产建议、真实持仓、风险提醒和最终盈亏能够一致、可追溯，并在此基础上生成下一个交易日策略。

## 1. 成功标准

本轮不以报告数量、新闻数量或测试数量作为成功标准。完成后必须满足：

1. 运行服务能够暴露实际代码版本和启动时间，磁盘代码与生产进程不再无法区分。
2. 每个真实持仓都有一条有效的止损/目标监控记录；缺失时系统明确失败关闭。
3. 已平仓亏损标的自动进入冷却状态，不会继续作为普通 `watching` 候选反复出现。
4. 盘中决策能够读取带时间戳的 K 线、资金流和市场环境数据，并拒绝过期数据。
5. 次日报告、统一入场闸门、持仓真值和候选池状态使用同一个目标交易日。
6. 真实成交继续保持人工确认边界，不接入自动下单。
7. 下一个交易日策略通过隔离副本生成并核验，验证期间不污染真实持仓、不推送飞书。

## 2. 方案比较

### 方案 A：只修报告文案

优点是改动小、交付快。缺点是实时止损、候选生命周期、运行版本和数据新鲜度仍然断裂，不能提高盈利证据质量。

结论：拒绝。

### 方案 B：修复盈利真值链，新增策略只做影子实验

修复运行版本、持仓监控、亏损冷却、盘中快照和日期闸门；两根 K 线确认与市场环境只生成对照样本，不影响真实买卖建议。

优点是先降低错误提醒和错误归因风险，同时为后续寻找正期望策略建立可靠样本。缺点是短期不会因为增加新指标而显著增加交易次数。

结论：推荐。

### 方案 C：立即修改生产买点和止损参数

优点是表面上更接近“直接提高收益”。缺点是当前没有足够完整的真实成交归因，也没有生产策略对照实验，直接修改会把真实账户变成无基线试验。

结论：拒绝。

## 3. 本轮实现范围

### 3.1 运行版本真值

- 健康接口增加当前 Git commit、进程启动时间和策略版本。
- 调度日志在任务开始时记录同一版本标识。
- 不自动重启服务；代码和测试验证通过后，再单独核验 launchd 重启边界。

### 3.2 持仓与风险监控对账

- 新增持仓监控对账函数，以 `user_portfolio.json` 为持仓真值。
- 已持仓但缺少监控计划时，创建明确标记为自动补全的计划，止损和目标沿用当前策略 profile 的确定性规则。
- 报告必须区分“人工设定止损”和“系统补全止损”。
- 对账失败时允许卖出/止损安全动作继续，但禁止新的买入/加仓建议。

### 3.3 平仓与候选池生命周期对账

- 已平仓且收益为负的标的自动转为 `cooldown_after_loss`。
- 保存冷却原因、平仓日期、已实现收益率和来源。
- 冷却标的不能被池外扫描或普通评分重新提升。
- 不回填或伪造旧信号身份。

### 3.4 盘中数据新鲜度

- 为盘中决策定义统一快照契约：`quote`、`kline`、`fund_flow`、`market_regime`、`captured_at`、各数据源状态。
- 夜间评分结果可以保存快照引用；盘中扫描必须刷新价格和关键字段。
- 缺失或过期时返回具体阻断原因，不使用空字典冒充中性数据。

### 3.5 日期与统一闸门

- 报告生成、候选评分和闸门保存共用解析后的目标交易日。
- 服务启动或盘中扫描时发现闸门过期，禁止新开仓并输出明确原因。
- 止损、卖出、取消入场等安全动作不被闸门拦截。

### 3.6 影子策略

- “关键位置连续两根 K 线确认”作为 `two_bar_confirmation_v1` 影子字段记录。
- “市场风格轮动”作为 `market_regime_v1` 影子字段记录。
- 两者本轮不改变生产建议、仓位或止损，只积累同机会对照样本。
- RSI/MACD 暂不实现；低质量重复直播内容拒绝进入策略层。

## 4. 数据流

```text
portfolio truth
  -> position-watch reconciliation
  -> risk health
  -> visible decision gate

closed positions
  -> candidate lifecycle reconciliation
  -> cooldown_after_loss

market sources
  -> timestamped decision snapshot
  -> production playbook
  -> shadow two-bar/regime observations

signal
  -> authorization
  -> recommendation
  -> manual fill
  -> outcome
```

本轮保证既有审计字段不被覆盖；历史缺少 `signal_id` 或 `recommendation_id` 的成交保持“未归因”，不能根据结果倒推填充。

## 5. 错误处理与安全边界

- 任一持仓缺少有效风控计划：禁止新开仓，保留卖出和止损。
- 关键行情数据过期：候选保持观察，报告写出具体缺失字段。
- 闸门日期过期：禁止新开仓，不影响风险动作。
- AI 调用失败：标记为降级，不把“已配置”表述成“已参与本次决策”。
- 不修改真实成交、不自动下单、不删除日志、不回填无法证明的旧归因。

## 6. 测试设计

所有行为修改采用测试先行：

1. 持仓缺少监控计划时，测试先证明当前不会补全或不会失败关闭。
2. 亏损平仓仍为 `watching` 时，测试先证明当前生命周期错误。
3. 盘中快照缺少 K 线/资金流/市场环境时，测试先证明当前错误地继续决策或缺少明确阻断。
4. 闸门日期与目标交易日不一致时，测试新开仓被阻断、安全动作保留。
5. 健康接口测试版本和启动时间字段。
6. 最后运行全量 pytest、Ruff、shell/plist 检查和隔离报告生成。

## 7. 下一个交易日策略交付

优化验证完成后：

1. 复制真实持仓、候选池和监控计划到临时目录。
2. 禁用飞书推送。
3. 使用最近一个完整收盘日数据生成报告。
4. 核验报告、闸门、临时持仓和候选池状态一致。
5. 输出持仓动作、新开仓动作、触发价、金额、止损、目标和失效条件。

如果目标日期是非交易日，策略自动服务下一个 A 股交易日，并明确显示具体日期。

## 8. 暂停条件

- 需要修改真实持仓或真实成交记录。
- 需要自动下单或扩大资金权限。
- 需要重启生产服务但无法证明 launchd 目标和当前进程一致。
- 最新行情、交易日或账户真值无法核验。
- 全量回归出现无法在本轮安全修复的失败。
