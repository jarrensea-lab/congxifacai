# 运行链路恢复设计

## 目标

在不改动真实持仓、标的池、易淘金权限和飞书凭证的前提下，恢复预测采集/回填的独立可用性，提高飞书瞬时故障下的投递成功率，并确认最新主线的 Sentinel 兜底链路可用。

## 已确认根因

1. 预测采集逐只串行获取 K 线；目标池规模增大后，单次任务超过 300 秒。
2. Scrapling 在 `async` 方法内执行同步网络请求，使名义并发实际串行；历史回填在本机缺少离线数据时也会落入同一路径。
3. 腾讯批量报价把 86 只标的一次塞入单个请求，供应商在 60 至 80 只之间开始返回空结果；目标池中的 ETF 代码还会让整批解析失败。
4. 采集和回填共享一个异常边界；采集超时会直接跳过回填，积压因此继续扩大。
5. 飞书 API 与 Webhook 都只尝试一次；瞬时网络错误会把整份夜间主报告记为投递失败。
6. 常驻服务仍运行在比 `origin/main` 落后 60 个提交的旧分支，未包含主线中已验证可返回新闻的 AKShare Sentinel 兜底。
7. 易淘金失败来自 macOS Accessibility 权限缺失，代码已按失败关闭处理；这不是可以安全绕过的程序错误。

## 方案

- 腾讯报价按 50 只分批；单个不支持的市场代码只跳过自身，不再清空有效股票报价。
- 预测采集和远程回填用可取消的腾讯 HTTP K 线源做有界并发，并给单标的请求设置超时；失败的标的记入结构化原因，不阻塞其他标的。
- Scrapling 的同步调用移入工作线程，避免其他使用方阻塞事件循环。
- 调度器把采集和回填拆成独立异常边界；无论采集是否超时，回填都会执行一次。
- 飞书 API 与 Webhook 各自做有限重试并使用短退避；配置缺失不重试，避免无意义请求。
- Sentinel 不另造第三套数据源；保留主线已有的 Tushare 主源 + AKShare 兜底，并用临时目录做真实只读数据验证。
- 易淘金继续失败关闭，仅报告需要用户在系统设置中恢复权限，不自动修改 TCC 或真实账户数据。

## 边界

- 不发送真实交易、不修改真实持仓/标的池、不写易淘金观察列表。
- 测试不得向真实飞书群发消息。
- 不覆盖旧脏分支；修复在独立 worktree 完成。
