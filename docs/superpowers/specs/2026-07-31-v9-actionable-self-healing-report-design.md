# 恭喜发财 v9.0：可执行机会与自愈报告系统设计

> 日期：2026-07-31
> 目标版本：`v9.0.0-dev`
> 状态：已实现，待生产常驻服务验收
> 安全边界：只生成研究、策略与风控建议；不自动下单，不绕过人工确认。

## 1. 目标

v9.0 不再把“生成了一份报告”视为完成，而以以下结果为完成标准：

1. 每个交易日主动扫描市场，而不是只复核旧候选池。
2. 先按真实账户现金和最小交易单位过滤，正文只推荐用户当前买得起的股票。
3. 每只新标的都说明综合评分、入选原因、操作条件和最大计划亏损。
4. 每日交代新增、保留、降级和剔除变化；状态未变化的旧标的不重复长篇解释。
5. 管线每一阶段都能证明输入、输出、数据时间和运行结果。
6. 数据源、评分、报告或推送断线时能够限次重试、从有效快照恢复或明确告警。
7. “抓到 0 条”“空报告”“日志写完成但产物缺失”不得再被判定为成功。

成功不等于保证盈利。系统优化目标是提高可执行机会的预期收益，并用硬止损、仓位和复盘限制错误成本。

## 2. 已确认的产品原则

### 2.1 操作优先

系统先读取真实账户快照，计算：

- 可用现金；
- 必须保留的现金安全垫；
- 单票可执行预算；
- 每只股票的最小交易单位和一手金额；
- 单笔最大风险金额。

一手金额超过可执行预算的股票不进入正文推荐，也不占用前三名名额。它可以留在后台研究归档；现金增加后，系统在下一次全市场扫描中重新判断，不需要人工恢复。

### 2.2 简洁优先

用户正文只回答：

1. 今天能不能操作；
2. 最多三只当前可操作标的；
3. 为什么入选；
4. 买多少、什么价格、止损和目标；
5. 今天新增、降级和剔除了谁；
6. 管线是否完整，若不完整缺在哪一段。

评分明细、数据源状态、模型原文和失败堆栈保留在本地审计区，不占用主要决策注意力。

### 2.3 评分不是唯一决策

高分不自动等于买入。股票同时满足以下条件才可进入“可操作”：

- 当前账户买得起最小交易单位；
- 必需数据完整且新鲜；
- 综合评分达到门槛；
- 突破或回踩交易剧本已经触发；
- 市场环境没有阻断该剧本；
- 止损距离和单笔风险符合账户约束；
- 未触发追高、退市、ST、流动性或长期逻辑红线。

所有真实交易继续由用户人工决定和执行。

## 3. 方案比较与选择

### 方案 A：在 v8.2 上局部修补

修复扫描顺序、报告过滤和个别重试。

优点是改动小。缺点是任务状态仍散落在日志和 JSON 中，无法可靠判断哪个阶段断线，也无法证明自动补跑是否完成。

### 方案 B：v9.0 阶段化管线与自愈闭环

建立统一的每日运行、阶段账本、产物校验、生命周期事件和恢复策略。

优点是能够同时解决“没有主动推标的”“候选无法晋级”“报告隐藏变化”和“断线不自愈”。缺点是涉及报告、生命周期、调度、运行状态和版本真值的联合改造，需要完整回归。

### 方案 C：只增加外部守护进程

服务退出时重新启动。

优点是部署简单。缺点是无法识别 HTTP 200 但数据为零、任务捕获异常后返回、报告内容为空等语义失败。

### 决策

采用方案 B，版本定为 `v9.0.0-dev`。进程级守护继续保留，但不替代业务阶段自愈。

## 4. 端到端管线

每日机会管线固定为：

```text
账户快照
→ 全市场发现
→ 可交易与可负担过滤
→ 数据补齐
→ 综合评分
→ 生命周期裁决
→ 报告渲染
→ 内容校验
→ 推送
→ 交付验真
```

### 4.1 账户快照

输入为本地持仓真值和易淘金只读账户快照。输出统一的：

- `available_cash`
- `total_assets`
- `reserve_cash`
- `executable_budget`
- `snapshot_at`
- `freshness`

券商快照不可用时，使用最后一个仍在允许时效内的账户快照，并在报告标记“账户数据降级”。超过时效则禁止新增买入建议，但继续完成市场扫描和观察报告。

### 4.2 全市场发现

全市场发现不再只依赖单一的低价正资金流表，至少覆盖：

- 量价突破；
- 回踩企稳；
- 资金持续流入；
- 板块相对强度；
- 新闻或公告催化；
- 中长期质量改善。

发现阶段只产生宽候选和证据，不直接产生买入动作。每个交易日必须记录扫描股票总数、各规则命中数和数据截止时间。

### 4.3 可交易与可负担过滤

在完整评分前应用硬过滤：

- A 股可交易状态；
- 非 ST、非退市整理；
- 流动性达到最低要求；
- 最小交易单位有效；
- 一手金额不超过账户可执行预算。

被预算过滤的股票只计入后台汇总，不进入正式候选池，不产生永久 `research_only` 身份。账户现金变化后可自然重新参与筛选。

### 4.4 数据补齐

对过滤后的宽候选补齐：

- 实时或有效收盘行情；
- K 线和量价结构；
- 个股资金流；
- 财务与估值；
- 板块和市场环境；
- Sentinel 新闻证据；
- Serenity 或长期 thesis 约束。

每个字段携带来源、时间和状态。空对象不得标记为 `ok`。必需字段缺失时，股票仍可进入“数据待补”审计，但不能晋级为可操作。

### 4.5 综合评分

v9 使用版本化的 100 分综合评分卡：

| 维度 | 权重 | 核心问题 |
|---|---:|---|
| 趋势与量价 | 30 | 是否形成有效突破或健康回踩 |
| 资金行为 | 20 | 主动资金是否持续、是否与价格确认 |
| 行业与催化 | 15 | 板块是否走强，催化是否具体且新鲜 |
| 基本面与估值 | 15 | 经营质量、估值和长期红线是否支持 |
| 市场相对强度 | 10 | 是否跑赢指数和所属板块，市场环境是否允许 |
| 风险收益质量 | 10 | 止损、目标、盈亏比和波动是否合理 |

账户可负担性、数据完整性、可交易状态和剧本触发属于硬门，不通过时不得靠加分绕过。

用户正文只展示：

- 综合分和等级；
- 最关键的三条加分理由；
- 一条主要风险；
- 操作或等待条件。

等级约定：

- `S`：85–100，且全部硬门和交易触发通过；
- `A`：75–84，优先观察，触发后可进入可操作；
- `B`：65–74，保留观察；
- `C`：低于 65，降级或剔除。

最终动作由“分数 + 硬门 + 交易触发”共同决定，不由分数单独决定。

### 4.6 生命周期裁决

正式池对用户只呈现四类动作：

- `新增`：今天首次进入观察或可操作列表；
- `保留`：状态和核心逻辑未变化；
- `降级`：评分、数据、市场环境或交易触发转弱；
- `剔除`：逻辑失效、风险红线触发、持续低于留池线或数据长期失真。

内部状态保留 `watching`、`executable`、`removed` 和研究归档，但删除“动态发现后永久无法晋级”的单向身份。动态候选只有在确定性规则生成完整 `promotion_evidence` 后才能晋级：

- 评分规则版本；
- 数据时间；
- 综合分和分项分；
- 交易剧本；
- 账户预算；
- 止损、目标和风险金额；
- 所有硬门结果。

AI 文本不能直接晋级标的；确定性规则可以生成只读推荐，真实买入仍需用户确认。

### 4.7 报告与变更清单

飞书正文结构固定为：

```text
今日结论：不买 / 可操作 N 只
账户：可用现金 / 安全垫 / 单票预算

可操作标的（最多 3 只）
股票、综合分/等级、三条理由、主要风险
触发价、股数、占用现金、止损、第一目标、最大计划亏损

今日变化
新增、降级、剔除及原因

管线状态
完整 / 降级；缺失阶段和影响
```

如果没有可操作标的，报告仍必须给出：

- 扫描股票数量；
- 买得起的数量；
- 完成评分的数量；
- 最接近触发的观察标的；
- 今日新增、降级和剔除；
- 没有买入建议的具体原因。

本地完整报告附加全部评分、数据缺口、研究证据和阶段审计。

## 5. 自愈与运行真值

### 5.1 阶段账本

新增 SQLite `PipelineRunStore`，每次运行以 `run_id + trade_date + pipeline_version` 唯一标识。

每个阶段记录：

- `status`: pending/running/succeeded/degraded/failed
- `attempt`
- `started_at` / `finished_at`
- `input_count` / `output_count`
- `data_cutoff_at`
- `artifact_path` / `artifact_digest`
- `error_code`
- `recovery_action`

阶段写入必须原子化。重复补跑使用同一 `run_id`，不得重复写候选、重复推送或覆盖更晚的成功结果。

### 5.2 语义健康检查

以下情况判定为失败或降级，而不是成功：

- 交易日全市场扫描为 0；
- 数据源发生重定向、登录页或非预期内容；
- 应评分数量与实际评分数量无法对账；
- 生命周期变化没有对应评分或原因；
- 报告不存在、为空或缺少核心章节；
- 报告写“暂无”但阶段账本存在新增候选；
- 推送接口返回成功但交付状态和报告摘要不匹配；
- 数据时间超过阶段允许的新鲜度。

### 5.3 恢复策略

- 网络瞬时失败：指数退避，最多 3 次。
- 主数据源失败：切换允许的备用源，并标记来源降级。
- 单只股票失败：隔离该股票，继续处理其他股票。
- 阶段失败：从上一个校验通过的产物恢复，不从头重复外部请求。
- 进程重启：启动后读取未完成运行并继续。
- 报告或推送失败：只重跑渲染、校验或交付阶段，不重新改变生命周期。
- 上游长期失效：停止生成可操作动作，继续产出降级报告并明确告警。

### 5.4 守望与补跑

保留 launchd 的进程 `KeepAlive`，新增业务守望任务：

- 20:30：执行每日机会主管线；
- 20:45：检查阶段完整性并补跑可恢复失败；
- 21:15：最终交付验真，未完成则发送故障告警；
- 服务启动：检查当日已到期但未完成的管线；
- 次日盘前：校验昨日报告与今日账户快照，必要时生成盘前校准。

高频盘中任务继续只监控正式池和持仓；全市场发现与每日主报告分离，避免高频请求失控。

## 6. 版本真值

新增单一版本模块，统一提供：

- 产品版本：`v9.0.0-dev`
- 管线版本：`actionable_pipeline_v1`
- 评分版本：`composite_score_v1`
- Git commit
- 进程启动时间

FastAPI、健康接口、调度日志、飞书标题、README、CHANGELOG 和报告元数据必须读取同一来源。不得再混用 V7、V7.5、V8.0 和 V8.2 文案。

生产服务标签可继续保持兼容；版本判断不得依赖 launchd label。部署迁移必须先验证新进程健康，再停止旧进程。

## 7. 错误处理与安全边界

- 不记录或推送 API Key、Cookie、Token、账户明细和异常堆栈中的敏感内容。
- 数据不完整时禁止新增买入动作，但持仓止损、退出和风险告警继续有效。
- 自愈不得通过放宽评分、伪造数据、重复外部付费请求或跳过风险门实现。
- 所有自动恢复有次数、时间和幂等限制。
- 任何写券商自选股的动作继续与交易动作隔离；v9 不新增自动下单能力。

## 8. 测试与验收

实施采用 TDD，至少覆盖：

1. 账户可执行预算先于完整评分生效。
2. 买不起的股票不进入前三名和正式候选池。
3. 动态候选通过完整确定性证据后可以从观察晋级，不再永久锁死。
4. 新扫描标的在同一次运行中完成数据补齐和评分。
5. 新增、保留、降级、剔除事件均有明确原因。
6. 空 Sentinel/Serenity 不得标记为健康。
7. 交易日扫描为 0 会触发失败、备用源和限次重试。
8. 阶段失败后能从最后有效产物恢复且不重复写入。
9. 报告隐藏候选、缺少变化清单或内容为空时校验失败。
10. 推送失败可重试，最终交付状态与报告产物一致。
11. 所有用户可见位置返回同一个 v9 版本真值。
12. 使用临时持仓、候选池、运行库和报告目录完成端到端测试，不污染真实账户数据。

交付验收需要同时满足：

- 聚焦测试和完整后端测试通过；
- lint、格式和 `git diff --check` 通过；
- 临时数据端到端运行生成有效报告；
- 人为注入数据源失败后，自愈或降级行为符合设计；
- 报告正文符合“可操作优先、最多三只、变化必交代”；
- PR 的 CI、mergeability 和实际提交版本可验证。

## 9. 实施边界与交付顺序

本次 feature 覆盖：

1. v9 版本真值；
2. 阶段账本与每日机会编排；
3. 可负担优先的发现与评分；
4. 可审计晋级和生命周期变更；
5. 简洁主报告与完整后台审计；
6. 语义健康检查、自愈和交付验真；
7. 测试、运行手册、CHANGELOG 和 PR。

本次不覆盖：

- 自动下单；
- 自动修改用户风险偏好；
- 无上限的全市场盘中高频抓取；
- 根据少量样本自动改评分权重；
- 绕过券商权限、登录或安全校验。

实施顺序为：版本与契约测试 → 阶段账本 → 发现和可负担过滤 → 综合评分 → 生命周期 → 报告 → 自愈守望 → 端到端验收 → PR。
